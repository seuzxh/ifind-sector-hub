设计方案

六个模块各管一段：过滤、凭据、数据源、存储、编排、服务。SectorHub 门面把它们组合起来，共享同一 token 管理与库文件。全景见 组件架构图。

1. 总体分层

消费方 (monitor 等)
  ├─ SDK 直用 ──────────► SectorHub ──┬─► IFindClient ──► iFinD API (接口1-6, smart_pick)
  └─ HTTP (可选 FastAPI) ─┘           │        │ 401
                                      │        ▼
                                      │   TokenStore / FileTokenStore ──► token.json (flock)
                                      │
                                      ├─► SectorSync（并发编排，复用 client + store）
                                      └─► SectorStore ──► SQLite 三表（快照语义）

依赖方向单向：sync → client + store + codes，client → tokens，hub → 全部，service → hub。 IFindClient 完全配置注入（base_url / timeout / max_retries / batch_size 构造传入）， 不再读任何全局配置；headers（含 access_token）由客户端自持，刷新后原地更新。

2. Token 生命周期 详见时序图

完整交互见 access_token 401 刷新时序图。设计要点：

2.1 双检锁（Double-Check）

refresh_access_token(stale_token) 进入 threading.Lock 后，先重新加载当前 token： 若已不等于调用方传入的 stale 值，说明本进程其他线程刚刚刷新过，直接复用、不再打刷新接口。 这把"8 个并发线程同时收到 401、连刷 8 次 token"收敛为 1 次接口调用。

2.2 跨进程共享（FileTokenStore）

FileTokenStore 把 token 存为 JSON 文件，写路径加 fcntl 文件锁， 在进程锁之外再做一次跨进程双检：锁内发现文件里的 token ≠ 本次 stale 值，说明别的进程刚刷过，采纳文件值。 同机多消费方共用一个账号时，刷新结果与 REFRESH_TOKEN 轮换自动共享——取代旧实现正则改写 config_local.py 的做法。

2.3 仅重试一次

IFindClient._post 收到 401 → 刷新 → 仅重试本轮一次：刷新后的请求若再 401，走完剩余重试后抛出， 防止"token 无效 ↔ 刷新"死循环。REFRESH_TOKEN 轮换由接口返回新值并自动持久化。

3. 客户端重试内核

场景行为
HTTP 401经 TokenStore 刷新后重试本轮（仅一次），不算入网络重试次数。
网络异常 / 5xx指数退避 sleep(2^attempt)，默认重试 3 次后抛出。
批量接口分片批大小默认 100（接口1 个股概念、接口5 概念信息），逐批请求。

接口覆盖：接口1 个股所属概念、接口2 概念成分股（p03473 data_pool）、接口3 历史日K、接口4 高频 1min K、 接口5 概念基本信息、接口6 实时行情快照（含批量），以及 smart_stock_picking 智能选股 （smart_pick_boards 枚举指数板块 / smart_pick_stocks 自然语言选股）。

4. 三表存储与快照语义

4.1 数据模型

表主键日期字段说明
ths_concept_dict concept_code update_date（YYYY-MM-DD） 概念字典：名称、全称、指数代码、主代码；永久缓存，replace 全量刷新。
concept_members (concept_code, stock_code, member_date) member_date（YYYYMMDD） 概念成分股；索引 idx_cm_concept。
stock_concept_map (stock_code, concept_code, map_date) map_date（YYYY-MM-DD） 个股-概念映射（含权重，默认 1.0）；索引 idx_scm_concept。

4.2 MAX(date) 快照语义

所有读方法（get_concept_members / get_concept_members_map / get_stock_concepts 等） 不传日期时，子查询取 MAX(date) 作为"最新快照"再过滤——同一天多次同步或历史数据并存时， 读到的始终是最新一份，且历史不清理（永久缓存语义，自 monitor 原样迁移）。 全市场股票池（get_all_member_stock_codes / get_mapped_stock_codes）同样基于最新快照去重。

4.3 幂等写入

三表写入统一 INSERT OR REPLACE，以主键天然幂等——同日重跑同步管线不产生重复行。

5. replace 级联与同事务迁移钩子

概念字典是"全量 replace"：当上游板块列表变化（概念下线/更名）时，replace_concept_dict(boards, migrate_hook) 在单个事务内完成：

  1. 删除新字典中已不存在的概念码（级联清理成分股与映射表中该概念的行）；
  2. 更名概念同步更新名称；
  3. 在同一连接、同一事务内调用 migrate_hook(conn, ...)——消费方借此迁移自己的关联表（如 monitor 的 watched 勾选从旧码迁到新码、清理失效勾选），要么全成要么全不成；
  4. 返回统计（迁移明细、被丢弃的 watched 列表）。

6. 同步编排 详见流程图

完整管线见 板块数据同步编排流程图。核心决策：

  • 并发内核：ThreadPoolExecutor（默认 8 并发）逐概念拉接口2；单概念失败只记 WARN 不中断，失败码在末尾汇总打印；进度计数器加锁，每 100 个概念输出一次进度。
  • A股过滤前置：字典初始化先过滤海外概念（861/864/865/871/875 前缀）；成分股入库可选 stock_filter（默认用 is_a_share_code 过滤非沪深北代码）。
  • 全集补全回路：init_concept_universe 从成分股表最新快照反查全市场股票池 → 接口1 逐批扫描每只股票的概念 → 反向收集字典未覆盖的新概念码 → 接口5 补字典、接口2 补成分股。支持 skip 开关（原"板块池启用仅 884"语义）与调用方口径的 existing_codes。
  • 观察池刷新：refresh_dict_and_members 对给定码集"接口5 刷字典 + 接口2 并发刷成分股"一步完成。

8. 兼容性决策记录

决策理由
保留三表日期格式不一致（YYYY-MM-DD vs YYYYMMDD） monitor 历史数据与查询口径依赖原格式；统一格式的迁移成本与风险大于收益。消费方按表注意即可。
三表 DDL 原样保留（含索引） monitor 直接把 SectorStore 指向既有 sector_attribution.db，零数据迁移。
同步日志前缀（[INIT] / [UNIVERSE] / [REFRESH] / [WARN]）原样迁移 运维侧已有基于这些前缀的检索习惯。
token 环境变量兜底（IFIND_ACCESS_TOKEN / IFIND_REFRESH_TOKEN） 首次 bootstrap 无需改代码；接入 FileTokenStore 后以文件为准。
