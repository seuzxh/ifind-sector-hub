设计方案

六个模块各管一段：过滤、凭据、数据源、存储、编排、服务。SectorHub 门面把它们组合起来，共享同一 token 管理与库文件。全景见 组件架构图。

1. 总体分层

消费方 (monitor 等)
  ├─ SDK 直用 ──────────► SectorHub ──┬─► IFindClient ──► iFinD API (接口1-6, smart_pick)
  └─ HTTP (可选 FastAPI) ─┘           │        │ 401
                                      │        ▼
                                      │   TokenStore / FileTokenStore ──► token.json (flock)
                                      │

依赖方向单向：sync → client + store + codes，client → tokens，hub → 全部，service → hub。 IFindClient 完全配置注入（base_url / timeout / max_retries / batch_size 构造传入）， 不再读任何全局配置；headers（含 access_token）由客户端自持，刷新后原地更新。

2. Token 生命周期 详见时序图

完整交互见 access_token 401 刷新时序图。设计要点：

2.1 双检锁（Double-Check）

refresh_access_token(stale_token) 进入 threading.Lock 后，先重新加载当前 token： 若已不等于调用方传入的 stale 值，说明本进程其他线程刚刚刷新过，直接复用、不再打刷新接口。 这把"8 个并发线程同时收到 401、连刷 8 次 token"收敛为 1 次接口调用。

2.2 跨进程共享（FileTokenStore）

FileTokenStore 把 token 存为 JSON 文件，写路径加 fcntl 文件锁， 在进程锁之外再做一次跨进程双检：锁内发现文件里的 token ≠ 本次 stale 值，说明别的进程刚刷过，采纳文件值。 同机多消费方共用一个账号时，刷新结果与 REFRESH_TOKEN 轮换自动共享——取代旧实现正则改写 config_local.py 的做法。

2.3 仅重试一次

IFindClient._post 收到 401 → 刷新 → 仅重试本轮一次：刷新后的请求若再 401，走完剩余重试后抛出， 防止"token 无效 ↔ 刷新"死循环。REFRESH_TOKEN 轮换由接口返回新值并自动持久化。

4. 三表存储与快照语义 配数据模型图

4.1 数据模型

三表结构与相互依赖（主键、concept_code 逻辑外键、读时 JOIN、级联清理、股票池派生）的可视化见 三表数据模型图，表结构如下：

表主键日期字段说明
ths_concept_dict concept_code update_date（YYYY-MM-DD） 概念字典：名称、全称、指数代码、主代码；永久缓存，replace 全量刷新。
concept_members (concept_code, stock_code, member_date) member_date（YYYYMMDD） 概念成分股；索引 idx_cm_concept。
stock_concept_map (stock_code, concept_code, map_date) map_date（YYYY-MM-DD） 个股-概念映射；写入时等权分配 weight = 1/N（N 为该股概念数，DDL 的 DEFAULT 1.0 仅兜底）；索引 idx_scm_concept。

4.2 MAX(date) 快照语义

所有读方法（get_concept_members / get_concept_members_map / get_stock_concepts 等） 不传日期时，子查询取 MAX(date) 作为"最新快照"再过滤——同一天多次同步或历史数据并存时， 读到的始终是最新一份，且历史不清理（永久缓存语义，自 monitor 原样迁移）。 全市场股票池（get_all_member_stock_codes / get_all_mapped_stock_codes）同样基于最新快照去重，SQL 内联 LIKE '%.SH'|'.SZ'|'.BJ' 只返回沪深北代码。

4.3 读访问器族与返回增强

  • 批量读：get_concept_members_map(codes) 单连接一次 SQL 取多个概念的最新成分股（按 concept_code / stock_code 排序），避免逐概念建连接——同步与消费方的热路径。
  • JOIN 增强：get_stock_concepts(stock_code) 联表 ths_concept_dict，直接返回 concept_code + concept_name + weight 三元组，消费方无需二次查名。
  • 五个常用只读访问器（L296-339，monitor 各处裸 SQL 的统一入口）：get_concept_names、get_latest_member_date、get_latest_member_stock_names、get_all_member_stock_names（全历史 MAX(stock_name)）、get_latest_members_snapshot（最新快照全体成分，返回 (日期, {概念: [(代码, 名称)]})）。

4.4 连接与事务

每次操作经 _connect() 上下文管理器建立短连接：PRAGMA busy_timeout=5000 + PRAGMA synchronous=NORMAL， 正常路径 commit、异常路径 rollback 后抛出——多线程并发入库（同步内核 8 线程）与消费方同库读写共存时靠 busy_timeout 阻塞等待而非报错。

4.5 幂等写入

三表写入统一 INSERT OR REPLACE，以主键天然幂等——同日重跑同步管线不产生重复行。

5. replace 级联与同事务迁移钩子

概念字典是"全量 replace"：当上游板块列表变化（概念下线/更名）时，replace_concept_dict(boards, migrate_hook) 在单个事务内完成：

  1. 删除新字典中已不存在的概念码（级联清理成分股与映射表中该概念的行）；
  2. 更名概念同步更新名称；
  3. 在同一连接、同一事务内调用 migrate_hook(conn, ...)——消费方借此迁移自己的关联表（如 monitor 的 watched 勾选从旧码迁到新码、清理失效勾选），要么全成要么全不成；
  4. 返回统计（迁移明细、被丢弃的 watched 列表）。

6. 同步编排 详见流程图

完整管线见 板块数据同步编排流程图。核心决策：

  • 并发内核：ThreadPoolExecutor（默认 8 并发）逐概念拉接口2；单概念失败只记 WARN 不中断，失败码在末尾汇总打印；进度计数器加锁，每 100 个概念输出一次进度。
  • A股过滤前置：字典初始化先过滤海外概念（861/864/865/871/875 前缀）；成分股入库可选 stock_filter（默认用 is_a_share_code 过滤非沪深北代码）。
  • 全集补全回路：init_concept_universe 从成分股表最新快照反查全市场股票池 → 接口1 逐批扫描每只股票的概念 → 反向收集字典未覆盖的新概念码 → 接口5 补字典、接口2 补成分股。支持 skip 开关（原"板块池启用仅 884"语义）与调用方口径的 existing_codes。
  • 观察池刷新：refresh_dict_and_members 对给定码集"接口5 刷字典 + 接口2 并发刷成分股"一步完成。

8. 可选 FastAPI 服务层

8.1 SectorHub（SDK）与 HTTP 服务层的差异

两条使用路径面向不同消费方，不是替代关系——HTTP 层只是 hub 门面之上的薄适配：

维度SectorHub SDK（进程内）FastAPI 服务层（跨进程）
调用方式Python import，直接对象调用HTTP REST（3 个 GET + 1 个 POST）
消费方形态仅 Python、通常同机任意语言 / 跨机器：web 前端、其他后端服务、脚本
token 与库的归属每个消费方自持 IFIND_* 凭据与 db 文件路径服务端集中持有 token 与 SQLite，消费方零凭据、无需安装本包
能力面全量：client / store / sync 所有方法（含行情、smart_pick、replace 钩子）收敛为只读三端点 + 一个同步触发；无行情、无 smart_pick、无字典 replace
时延无网络跳变，函数级调用多一跳 HTTP 与序列化
部署成本pip install 即用需要部署并维护一个常驻进程（含鉴权/网络策略）

8.2 为什么是"可选"的 FastAPI

  • 多平台复用是抽离初衷：monitor 这类同进程 Python 消费用 SDK 就够；但非 Python 消费方（前端、其他服务）只能走 HTTP——两条路径都要有。
  • 凭据集中化：部署为服务后，iFinD 账号与 SQLite 只在服务端，消费方不接触凭据，也不必各自实现 token 刷新/并发同步。
  • 最小暴露面：HTTP 只开放"读快照 + 触发同步"，把写路径限制在受控的 POST /sync/members，不把整套 SDK 语义搬到网络边界。
  • 不破坏核心依赖约束：fastapi / pydantic 放在 [service] extra 里，SDK 用户的核心依赖仍然只有 requests；未安装时 import service 报 ImportError，不影响库核心。
  • 实现是 44 行薄适配：build_router(hub) 只做参数搬运与响应包装，零业务逻辑——门面模式保证 SDK 与 HTTP 行为一致。

9. 兼容性决策记录

决策理由
保留三表日期格式不一致（YYYY-MM-DD vs YYYYMMDD） monitor 历史数据与查询口径依赖原格式；统一格式的迁移成本与风险大于收益。消费方按表注意即可。
